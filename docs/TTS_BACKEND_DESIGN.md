# 交換可能なローカルTTS設計・API契約

2026-10-22。TTS_BACKEND_MIGRATION_TASKS.mdのT1〜T2を具体化する設計。

## 構成

発話サービス → RuntimeManager → モデル構成で起動したワーカー → Backend契約の実装。
翻訳・ASRは独立した補助ワーカーを所有し、TTS切替で終了しない。現時点ではOmniVoiceと同じPython環境の依存を再利用するが、TTSモデルのロードは行わない。

登録はアプリ同梱の明示的な辞書で行う。任意Pythonモジュールの実行指定は公開APIに持ち込まない。バックエンドIDは実装、モデル構成IDは重みと実行環境を指す。最初のモデル構成IDは`omnivoice`。未来のQwen実装は未搭載。

## Backend契約 v1

- `capabilities()`：対応言語、参照音声・文字起こしの要否、参照時間、話速、voice design、設定の型・範囲・初期値、完成WAV方式。
- `validate(reference, language, settings, speed)`：要求受付時の検証。推論ワーカー側でも再実行する。未対応設定は拒否。
- `installed(model_config)`、`identity(model_config)`：導入判定と固定版情報。パスの変更は新しい構成として扱う。
- `load()`：モデル読込とハードウェア情報。`prepare(reference)`：モデル固有の参照特徴の準備。`synthesize(request)`：合成。
- `design(request)`：能力がある場合だけ標準参照WAVを生成。
- unloadは所有ワーカーの終了。GPUのTTS処理は共有ロックで直列化し、切替時には前モデルを解放する。

共通要求は`model_id`、`voice_id`、`text`、`mode`、`speed`、`engine_settings`、要求ID等。旧`engine`はモデル構成IDの互換エイリアスで、両方の不一致は422。廃止済みIrodori・未知IDは422。選択モデルの言語非対応・設定不正も422。モデル未導入・声の未準備は503。ワーカーの異常・タイムアウト等はジョブの失敗として返す。

完成音声はPCM16モノラルWAVに変換し、元モデルのサンプルレートを維持。有限値、有音、30秒上限を検証する。結果にサンプルレート、チャンネル数、生成・参照時間、実際のモデル版と設定を含める。

## ジョブと資源

受付時にモデルID、実効設定、声の参照版、辞書版を固定。キュー中の画面変更は影響しない。実行時にモデル版の変更を検出したら失敗させ、勝手に新モデルへ置換しない。停止・取消はブラウザーを止め、遅い生成結果・履歴・キャッシュへの確定を防ぐ。実推論の中断は保証しない。

翻訳はCPUで元の日本語を受けて訳文を返し、失敗時にはTTSを呼ばない。ASRもCPUで参照区間だけを下書き認識し、保存済み参照は更新しない。補助サービスは専用の所有ワーカーを利用し、共有ロックでTTSと直列化する。

## 設定・声・キャッシュ

設定schema v3で`models`にモデル構成を保存する。共通のPython、ポート、オフラインと、モデル別Python・重み・manifest・デバイス・精度・初期設定を分ける。旧フラット設定は読み込み互換を持ち、保存時に旧ファイルをバックアップする。

元WAV・声ID・名前・お気に入り・参照区間・文字起こしはモデル非依存の素材。モデル固有の準備結果はモデルID・モデルidentity・素材ハッシュ・参照版で分離する。OmniVoiceの3〜10秒と文字起こし必須は能力定義へ置く。新しい標準4声はOmniVoiceのvoice designを使用し、既存WAVと手動参照設定は変更しない。新規生成は音声長を検証してから原子的に保存する。

キャッシュはモデル実装・重みrevision・実行設定・アダプターコードhash・声の素材/版・文/言語/辞書版・翻訳版で識別する。モデルのファイル時刻だけに依存しない。旧キャッシュと名前空間を分ける。履歴WAVと当時の出自は保持する。

設定DB移行はSQLite backup後に実施し、再実行しても追加変更しない。旧`japanese_engine=irodori`は保存設定の移行時だけOmniVoiceにする。外部要求で明示されたirodoriは拒否。旧`/api/speech`は410でジョブAPIへの移行を案内する。

## 検証と追加方法

OmniVoiceと異なる制約を持つテスト用Backendを同じRuntimeManager/発話サービスで動かし、固有名分岐なしで登録・発話・キャッシュ分離できることを検証する。実モデルは隔離ポートと検証データで日本語・翻訳・ASR・新規標準声を確認する。新規環境の導入と人の試聴・通話は別の検証項目。

バックエンド追加は契約実装、登録、モデル構成、導入スクリプト、契約テストを追加する。言語やステップ等の条件を共通サービスへ追加しない。リモート・ストリーミング・同時GPU常駐は対象外。
