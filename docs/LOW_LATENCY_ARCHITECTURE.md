# 入力から発話までの低遅延化設計案

2026-10-29。検討案。今回の変更は本書のみで、実装・設定変更・モデル追加・新規ベンチマークは行っていない。

## 結論

モデル交換可能な構成を維持し、完成音声を返すBackend v1に、音声を順次返すBackend v2を追加する。まず計測と文単位の先行再生を実装し、短文でも待ち時間が残る場合はネイティブ音声ストリーミング対応の実行系を比較する。

短文の低遅延が主目的なら、文分割よりストリーミングモデルの評価を先行してよい。WebSocketへの置換だけでは、全文合成完了待ちは解消しない。

導入済みOmniVoiceのsource_revisionは08be0b4ccbac3e13e374e86fbfead4b4cac343e2。ローカルgenerate実装には長文の内部分割があるが、現在のアダプターは完成結果のみ取得する。内部chunk処理と逐次再生APIは別物。generateには既にtorch.inference_modeが付いており、これを追加するだけの改善は見込まない。

2026-10-22の既存記録では、準備後の短文WAV取得中央値は32ステップ1,973.7ms、16ステップ1,187.3ms（各3回）。現在の再測定値ではなく、物理出力の時間でもない。既に状態変化通知と起動時の選択声準備は実装済み。詳細はLATENCY_IMPROVEMENTS_2026-10-22.md。

## 推奨する処理経路

```text
送信確定 → 要求・声・モデル・辞書の版を固定 → キャッシュ検索
                                      ↓ miss
                            正規化／必要なら翻訳
                                      ↓
                      発話スケジューラー → 専用TTSワーカー
                                             ↓ 順次PCM
ブラウザー AudioWorklet ← 音声ストリーム ← 検証／配信
                                             ↓ 同時に蓄積
                                   全文完了後にWAV保存
```

最初のPCM再生と、全音声の完成・履歴保存を分離する。TTSワーカーは常駐を継続し、モデル・声の切替時に準備する。起動時のダミー推論を追加するなら、履歴に残さず音も出さず、準備完了表示と分けて管理する。

### 1. モデル非依存の音声出力契約

- Backend v1のsynthesizeは互換用に維持する。
- v2はsynthesize_stream(request, cancel_token)からformat、audio_chunk、endまたはerrorを返す。
- 能力はaudio_output=complete/native_stream、text_input=complete/incremental、cancel=between_segments/cooperative等を別々に表現する。モデル名から推測しない。
- 文分割はサービス側のsegmentedモードとして表し、OmniVoiceのnative_stream能力を偽装しない。
- formatはsample_rate、channels、PCM形式を宣言。chunkはrequest_id、epoch、sequence、sample_offsetを持つ。1発話の途中で形式を変えない。
- ワーカーからAPIまでのIPCもバイナリーPCMを順次通す。完成Base64 JSONのままではブラウザーだけ変更しても効果がない。
- v1バックエンドは完成波形を一括で返して同じ再生経路へ接続できるが、初音の生成待ちは短縮されない。

### 2. 配信と再生

初期案は既存POSTジョブ受付と取消APIを維持し、ジョブ専用WebSocketを追加する。制御メッセージとバイナリーPCMを送り、取得側から受信量を通知してバックプレッシャーをかける。HTTPストリームでも実現可能だが、双方向の取消・流量制御をまとめやすい方式を選ぶ。

ブラウザーはAudioWorkletと上限付きリングバッファで再生する。初期バッファ80〜150msは実験開始値であり保証値ではない。モデルの初回チャンクが大きければそれが下限になる。モデル固有サンプルレートからAudioContext側への連続リサンプリングと境界処理を実装する。再生権限は従来どおりユーザー操作時に有効化する。

同一Origin・Host検証、ジョブ所有者の確認、接続期限・最大バッファを設ける。切断時に自動で最初から再生しない。再接続は受信済みsequence以降だけを復元できる場合に限定する。

### 3. OmniVoiceを維持する段階的な改善

送信後の文を意味の切れ目で分割し、最初の文が生成できたら再生、その間に次の文を生成する。例えば「こんにちは。今日は予定を確認します。」では最初の挨拶を先に再生する。短い一文には効きにくく、総生成時間が増える可能性もある。

句点・疑問符等を優先し、数字・単位・固有名詞を途中で切らない。最小長・最大推定音声長は評価で決め、最初から極短断片に固定しない。各文で声・設定を固定し、境界の抑揚・間・話者類似性を試聴する。文間の自然な間を一律削除しない。クロスフェードで子音を欠損させない。

無音除去は任意の後処理として別に比較する。現行の振幅しきい値をそのまま切断位置にせず、小さい語頭音を保護する余白を設け、切除上限と原音比較を用意する。これは推論高速化とは別の効果。

16ステップは既存の選択肢であり新しいアーキテクチャではない。速度優先プリセット候補として比較するが、保存済み32を無断で変更しない。

### 4. 短文の待ちをさらに減らすモデル評価

Qwen3-TTSは逐次音声生成の評価候補。公式リポジトリーと技術報告はストリーミング能力を説明しているが、モデルの能力と導入するPython API・推論サーバーが実際にPCMを順次返すことは別に検証する。公式の97ms等はこのPC・日本語クローン・ブラウザーでの到達値ではない。

- [Qwen3-TTS公式リポジトリー](https://github.com/QwenLM/Qwen3-TTS)
- [Qwen3-TTS技術報告](https://arxiv.org/abs/2601.15621)
- [OmniVoice公式リポジトリー](https://github.com/k2-fsa/OmniVoice)

評価環境を分離し、日本語・参照音声によるクローン・実チャンク出力・Windows/CUDAの動作を確認してから採用する。同じ元録音からモデル別の準備結果を作る。対応しない能力や失敗時に別の声・モデルへ自動変更しない。小型モデルも品質と初音時間を同じ条件で比較し、パラメーター数だけで採否を決めない。

### 5. キュー・取消・履歴

- CPU翻訳／準備、GPU合成、音声配信を別キューに分ける。補助ワーカー内の逐次実行とCPU負荷上限は維持する。
- GPUは原則1モデル・1発話の実行所有権を維持。通常発話を定型句の事前生成より優先し、バックグラウンド処理を文境界で譲る。
- 同じ発話の翻訳完了待ちは残る。翻訳を分割すると意味が変わり得るため、第一段階は全文翻訳後に音声分割する。
- 翻訳込みの定型句キャッシュは元文・翻訳版・モデル版・声の版・辞書版・全設定から事前検索できる索引を設ける。既存の確定版照合は維持する。
- 取消は再生バッファを即座に空にし、epochを更新する。旧epochの遅着音声は破棄。ワーカー中断は能力に従い、非対応なら結果を捨てて次の推論を待つ。毎回ワーカーを殺す方式は再ロード遅延があるため標準にしない。
- 状態はqueued、preparing、generating、streaming、completed、cancelled、failedを区別。completedは全チャンク生成・確定完了であり、端末の再生完了は別状態。
- チャンクごとの有限値・形式・長さ検証に加え全体30秒上限を維持。先頭の無音チャンクだけでエラーにせず、全体有音判定を行う。
- 途中失敗は既に聞こえた音を取り消せない。再生停止とエラーを表示し、完全な発話として履歴・定型句キャッシュを確定しない。完成WAVの検証を前提にしていた既存契約からの変更点として扱う。

## 計測と実装順序

| 順序 | 作業 | 採否・完了条件 |
| --- | --- | --- |
| 1 | 段階別計測、比較用文セット | 送信、キュー待ち、準備、翻訳、初回PCM、全生成、初回再生、有音開始を分離 |
| 2 | v2契約・PCM配信・AudioWorklet | 人工チャンクで順序、取消、欠損、切断、バッファ上限、サンプルレート変換を検証 |
| 3 | OmniVoice文分割と先行再生 | 長文の初音改善と、読み間違い・境界不自然さ・音切れの比較 |
| 4 | 逐次出力モデルの独立評価とアダプター | 短文でも初音改善、実時間を上回る生成速度、許容できる日本語音質を確認 |
| 5 | 翻訳／GPUキュー分離、キャッシュ経路改善 | バックグラウンド生成・翻訳中でも通常発話を不必要に止めない |
| 6 | UI・履歴・運用文書統合 | 従来WAV方式へ切戻し、バッチ起動停止、モデル変更・取消を通しで検証 |

短文、日本語長文、固有名詞・数字、翻訳、キャッシュ命中、起動直後、声変更、連続送信を別条件で測る。各条件は十分な反復（初期比較は30回以上）でp50/p95、初回有音、生成RTF、音切れ数を記録する。RTF<1は継続再生の必要な目安だが、チャンクごとの生成の揺れも評価する。

ブラウザーとPythonの時計は直接減算せず、各プロセスの区間時間と要求IDで対応付ける。AudioWorkletの再生時刻とOSループバックによる有音検出を比較し、物理スピーカー／通話相手の遅延は別途測る。ASRだけで自然さ・声の似方を合格扱いしない。

目標案は準備済み・日本語・空キューで送信から有音までp50 500ms以内、p95 1秒以内。達成済みの値ではなく、モデル比較で実現可能性を判断するための仮目標。現行OmniVoiceの文分割だけで短文も達成できるとは見込まない。

入力中の先読み合成は後段の任意機能とする。IME変換中は生成せず、編集で必ず無効化し、送信前には再生しない。無駄なGPU処理が確定した発話を遅らせないよう低優先度・上限付きで実行する。

## 変更対象

speech/backends/base.py（v2能力と契約）、speech/backends/omnivoice.py（準備ハンドル）、speech/worker.py・runtime.py（ストリームIPCと資源所有）、speech/service.py・jobs.py（段階処理と取消）、speech/audio.py（逐次検証と最終WAV）、app.py（配信API）、static/app.jsおよび新規AudioWorklet、契約・配信・実機ベンチマーク。

start.bat／stop.batの利用方法は維持できる。WebSocketやモデルごとのワーカー起動・停止は既存の管理プロセスの責任に含める。
