# Echo Ego：入力して話すアプリの検討・初期設計

検討日：2026-10-04。実装前の提案。性能値は未計測。

## 推奨構成

Windows PC上でモデルをGPUに常駐させ、テキスト確定後に短い発話を生成してスピーカーへ再生する。低遅延用モデルの第一候補は `Aratako/Irodori-TTS-v4.1-Small-MF`、比較基準は通常版 `Aratako/Irodori-TTS-v4.1-Small`。

最初はローカルWeb画面＋Pythonのアプリ制御層＋Irodori-TTS-Serverで検証する。操作と音声品質が固まったらデスクトップ化し、出力デバイス選択・常駐・グローバルショートカットを追加する。モデルの種類、バージョン、精度、生成ステップは記録・固定する。

```text
入力画面 → 確定・読み置換 → 優先度付き発話キュー
                           ↓
                 GPU常駐 Irodori-TTS
                           ↓
                 WAV受信 → 再生キュー → スピーカー
```

入力文字列や登録音声はローカルに置く。初期導入時のモデル取得を除き、発話ごとのクラウド通信は不要。LLMによる文章変換は基本経路に入れない。

## 現在の確認結果

- `nvidia-smi`：NVIDIA GeForce RTX 5080、VRAM 16,303 MiB。
- 既存のIrodori-TTS-ServerのソースとREADMEを確認。
- 既存 `.env`：通常版v4.1-Small、`model_precision=fp32`、`num_steps=40`、compile無効。
- `http://127.0.0.1:8088/health` は確認時に接続拒否。実際の合成時間、音質、音が出るまでの時間は未計測。
- 既存サーバーのソースは通常版の40ステップを明示的に既定値として使用する。最新公式READMEではモデル別既定値（RF 40、MF 4）に対応しているため、導入時にサーバーと推論ライブラリの互換性を確認する必要がある。

既存環境の設定は変更していない。会話用の別設定・別ポートで比較する。サーバーを分けてもGPUは共有されるため、他の合成処理と同時に走らせると待ち時間やVRAM競合が生じる。

## モデルの選択

| 候補 | 目的 | 判断 |
| --- | --- | --- |
| v4.1-Small-MF、4ステップ | 会話用 | 第一候補。少ステップ向けに蒸留されたモデル |
| v4.1-Small、40ステップ | 音質比較用 | 読みと声の再現性の基準 |
| 通常版の低ステップ＋Sway | 追加比較用 | 低ステップ時の品質を実聴して判断 |
| 量子化・別ランタイム | 第二段階 | VRAM節約と速度向上は別。実測が必要 |

公式MFモデルカードは、通常版を4ステップに落とす場合より読み精度と話者類似度を保ちやすいと報告している。ただし通常版40ステップと完全同等ではなく、人間が聞いた品質や会話の開始遅延を保証する評価ではない。

MFを使う場合は初期実験でリクエストに `irodori.num_steps=4` を明示し、モデルが正しくMFとして認識されていることを確認する。通常版の設定を流用して40ステップのままにしない。MFでは推論時CFGとSwayは適用されない。

## 遅延を減らす順序

1. **モデルを常駐させる。** 毎回CLIを起動したりモデルを読み直したりしない。起動時に実際の短い合成を行い、準備完了を表示する。health応答だけで準備完了にしない。
2. **MFモデルを評価する。** 4ステップを基準に、読み・声の類似性・余計な末尾発話を確認する。40→4のステップ減少はアプリ全体の10倍高速化を意味しない。
3. **参照音声を前処理する。** 対応するモデル・codecでlatentを事前生成し、毎回の録音読込・音声エンコードを省く。声の条件エンコードまでキャッシュする場合は推論実装の追加対応が必要か確認する。
4. **短いWAVを直接再生する。** 初期構成ではMP3変換、保存先選択、外部プレーヤー起動を挟まない。ブラウザーでは再生機構を初回操作時に準備し、受信・デコード後に再生する。
5. **定型句を事前生成する。** 「はい」「ありがとう」「少し待ってください」などは合成待ちを省ける。音声・モデル・読み・速度・スタイル変更時はキャッシュを更新する。
6. **生成と再生を重ねる。** 発話Aを再生している間にBを生成する。GPU生成は原則1件ずつとして会話の応答を優先する。
7. **必要なら句単位の分割を追加する。** 長文だけを自然な句・文境界で分け、最初の句ができたら再生しながら次を生成する。短文の細分化は不自然さと固定費増加を招きやすい。
8. **BF16とcompileは測定して採用する。** FP32からの変更は速度候補だが互換性・品質を確認する。compileには初回・形状変更時の待ち時間があり、可変長発話では常に有利とは限らない。

## ストリーミングの意味

通常APIは音声全体を生成した後に返す。SDKの `with_streaming_response` という名前だけでは生成途中の再生にならない。

公式の `stream_format: "sse"` は文章をチャンクへ分割し、各チャンクの合成終了後に `audio_chunk` を返す。チャンク内部の波形を生成途中から連続出力する方式ではない。一文が一チャンクならその一文の生成完了を待つ。

まずは短文全体を高速生成する方式を採用し、長文にだけSSEを使う。句分割では境界の声色・抑揚・間隔と、次の句の生成が再生に間に合うかを評価する。

## 自分の声・プリセット音声

自分の声は参照音声によるゼロショットクローンから始める。静かな環境で短い発話を複数録音し、合計約30秒を品質比較の出発点にする。公式評価では複数短文を連結した参照が使われている。遅延用には短い参照とも比較し、声の類似性と待ち時間の妥協点を選ぶ。学習は必須ではない。

プリセットは、使用条件を確認した固定の参照音声を登録する方式を基本にする。Voice Designで作った合成音声を参照として登録する方式も試せるが、再生成時の声の安定性を確認する。説明文だけから毎回声を設計する方式は、固定された人格の声としての一貫性を別途評価する。

初期実装ではLoRAやSpeaker Inversionの学習を必須にしない。参照クローンで満足できない場合に比較する。

## 会話用UIの要件

- 一文の入力、声の選択、発話、停止、再発話、定型句。
- Enterで発話。ただし日本語IMEの変換確定中は発話しない。Shift+Enterは改行。
- 発話後も入力欄にフォーカスを保ち、次の文をすぐ入力できる。未送信の入力は保持する。
- 生成中・再生待ち・再生中・準備中・エラーを区別して表示する。
- 通常は送信順で再生し、履歴の再発話は生成済み音声を先頭から再生する。
- 停止は再生と未再生キューを直ちに止める。進行中のGPU計算を中断できない場合も、戻ってきた旧結果は再生しない。停止後の新規発話がGPU待ちになる可能性は計測する。
- 入力内容、声、読み、設定に世代番号を付け、古い生成結果の誤再生を防ぐ。
- 生成履歴・録音の保存と削除はユーザーが選べる。

入力中の先読み生成は第二段階にする。IME確定後の固定部分や句点を候補にできるが、編集による無駄生成が本送信を遅らせないようにする。先読み結果は完全一致した場合だけ再利用し、送信前に発話しない。

## 性能の目標と検証

指標はEnterから**最初の聞こえる音**まで。HTTP応答時間、音声全体の生成時間、RTFだけでは代用しない。WAV先頭の無音、デコード、オーディオデバイスのバッファも含む。

設計上の仮目標：暖機後の10〜30文字程度の短文で中央値0.5秒以内、95パーセンタイル1秒以内。これは希望する使用感を表す受入目標であり、RTX 5080で達成済みという意味ではない。定型句は合成を省くため、一般短文とは別に測る。

比較対象：通常版40ステップFP32、MF4ステップFP32、互換性確認後のMF4ステップBF16。短い参照と約30秒の参照、初回と暖機後、10・30・60文字、声の変更、連続送信を比較する。モデル取得時間・起動時間は会話中の遅延から分けて記録する。

各条件で同じ文を複数回測定し、中央値・95パーセンタイル・最大値・VRAM使用量を記録する。種や入力の変動も評価に含める。固有名詞、数字、疑問文、短い相づち、句読点だけの入力を含める。

ブラウザー側で送信・受信・デコード・再生開始を記録する。実際の可聴開始はループバック録音または録音による音の検出で確認する。読み間違い、欠落、余分な発話、声の似方、長文の継ぎ目は実聴する。無音だけの入力はTTSへ送らず処理する。
