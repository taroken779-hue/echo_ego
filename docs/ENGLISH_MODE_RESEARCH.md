# 英語モード調査・構成案

調査日: 2026-10-19。対象: 現在のEcho Egoソースと公式公開資料。実装前の技術調査。

設計への反映: [OmniVoice統合設計](OMNIVOICE_INTEGRATION_DESIGN.md)を追加した。日本語・英語をOmniVoiceへ統一できるか比較し、読み辞書は日本語TTS直前だけに適用する。以下は初回調査として参照する。

追補: [Qwen3-TTS以外の候補比較](ENGLISH_TTS_ALTERNATIVES_2026-10-19.md)で、MOSS-TTS-Nano、CosyVoice 3、VoxCPM2、Chatterbox V3/Nano、MOSS Realtime、Pocket TTS、FireRedTTS3等を追加調査した。以下のQwen3-TTS第一候補という記述は初回調査の暫定案。モデル選定は、追補の3候補を含む実測比較で決める。

## 結論

日本語入力→翻訳→選択した声で英語発話という機能は、ローカル構成で実現を検討できる。現在のIrodoriに翻訳だけ追加する方式は採用できない。現行モデルは公式に日本語入力のみ対応と明記されている。[1]

日本語モードはIrodoriを残し、英語用TTSワーカーと翻訳処理を追加する。第一候補はQwen3-TTSのBaseモデル。まず0.6Bと1.7Bの速度・声の類似性を比較する。既存の声を使う要件では、プリセット専用CustomVoiceではなく参照WAVを扱うBaseが中心になる。[2]

低遅延化は可能性があるが、このPCで翻訳込みの発話開始時間は未計測。公称97msをアプリの応答時間として扱わない。最初の評価目標を「ウォーム状態・待ち行列なしの短文で再生開始まで中央値1.5秒以下、p95 3秒以下」と仮置きし、達成可否を実測する。これは予測値・性能保証ではない。

## 現在の構成と制約

| 箇所 | 現状 | 英語対応への影響 |
| --- | --- | --- |
| `app.py:81 generate()` | Irodori SamplingRequestで一括合成、WAV化 | 言語別TTSの分岐が必要 |
| `app.py:69 latent()` | Irodori用Codec特徴をキャッシュ | 他モデルと互換性なし。参照WAVから再抽出 |
| `app.py:44 voices()` / `resolve_voice()` | design / preset / custom、WAVを共通管理 | 声一覧と元WAVは再利用できる |
| `app.py:173 Speech` | 日本語想定160文字、voice/steps/speed | mode、入力言語、出力言語、ジョブIDを追加 |
| `app.py:181 spoken_text()` | 日本語の読み辞書を一律適用 | 翻訳前のかな置換は避け、翻訳用語集と分離 |
| `app.py:197 speak()` | 単一ロック、競合時409、完成WAV応答 | 翻訳とTTSの処理段階・キャンセルを管理 |
| `static/app.js:150 speak()` | 入力時の声・速度をキューへ保存 | モードと翻訳設定も送信時点で固定 |
| `static/app.js:160 pumpSynthesis()` | FIFO生成、409再試行 | 同じジョブの再送による翻訳や生成の重複を防ぐ |
| `static/app.js:173–174` | 全体arrayBuffer→decodeAudioData | 部分音声が届いても現状では早期再生できない |
| `static/app.js:75 stop()` | Abortと世代番号で古い結果を破棄 | サーバーのGPU処理停止とは別。ワーカー側取消も必要 |
| `store.py` / `static/features.js` | 設定・履歴・定型句・キャッシュ | 原文と訳文、言語、エンジン、モデル版を保存 |
| `configuration.py` / `scripts/start.ps1` | 単一Python環境とIrodori起動 | 英語ワーカーを別環境・別プロセスで管理 |

現状でも「前の音声の再生中に次の文を生成」はできる。ただし翻訳と音声生成を並列で先読みする仕組みはない。

今回のGPU照会ではRTX 5080、総VRAM 16,303 MiB、使用中6,131 MiBだった。使用量は瞬間値であり、利用プロセスの帰属や英語モデルの余裕を証明しない。既存サービスは停止・変更していない。

既存の`docs/IMPLEMENTATION.md`には日本語の初回API応答約0.98秒、キャッシュ約0.006秒という過去記録がある。今回は再計測していない。英語モデルの速度の根拠にはできない。

## 候補と判断

### 英語音声

| 候補 | 使い方 | 判断 |
| --- | --- | --- |
| Qwen3-TTS 12Hz Base 0.6B / 1.7B | 日本語参照WAVから声を条件付け、English指定で生成 | 第一評価候補。速さと似方を両モデルで比較 |
| Qwen3-TTS CustomVoice | 内蔵話者を選択 | 英語向け新規プリセットの選択肢。既存本人WAVのクローンとは別経路 |
| Chatterbox Multilingual | 多言語参照音声から英語生成を比較 | 声質比較用の代替候補 |
| Chatterbox Turbo | 英語用の軽量経路 | 英語参照を用意できる場合の比較候補。日本語参照からの品質を推定しない |

Qwen公式は日本語・英語、Baseによる声のクローン、参照プロンプトの再利用を説明している。通常は参照音声の文字起こしも使い、文字起こしを省く話者特徴のみの方式は品質が下がり得る。[2]

日本語WAVを入力できることと、その人が自然な英語で同じ声に聞こえることは別である。クロス言語時の似方・アクセント・明瞭さは実聴で判定する。必要なら本人の短い英語録音も比較する。

ChatterboxはMITの代替候補で、Multilingualと英語向けTurboを区別する。公式も参照言語が出力アクセントに影響し得る点を説明している。[5]

### 翻訳

| 候補 | 評価目的 | 注意点 |
| --- | --- | --- |
| Helsinki-NLP/opus-mt-ja-en | 軽量な日英翻訳の基準。CPU実行も比較 | 会話の省略、丁寧さ、固有名詞、否定、数字の品質を別途評価 |
| TranslateGemma 4B | 翻訳専用モデルによる品質比較 | 量子化を含むVRAMと速度を計測。Gemma利用条件の確認が必要 |

OPUS-MTは日英方向とApache-2.0がモデルカードに明記されている。[6] TranslateGemmaはGoogleの翻訳用モデルで、Gemma条件への同意が必要。[7] 今回はどちらもダウンロード・実行していない。TranslateGemmaの日英対応詳細と採用ランタイムの適合は導入前に追加確認する。

最初は翻訳モデルを固定し、正しい英訳だけを返す。解説や思考文を音声化しない。訳文が空、不完全、想定外の長さ、タイムアウトの場合は発話せず表示する。否定・数値・主語省略を含む入力セットで選定する。

クラウドAPIは通信時間・外部送信・利用料金が加わる別案。今回は既存のローカル方針を優先して採用比較の中心にしていない。契約・登録・外部への録音送信は行っていない。

## 推奨構成

```text
ブラウザー: 日本語入力 + 声選択 + 日本語/英語モード
    ↓ 送信確定（IME変換中には送らない）
FastAPI: ジョブ受付・設定の固定・キュー・取消
    ├─ 日本語 → 既存Irodoriワーカー
    └─ 英語 → 翻訳 → 確定した英語文 → 英語TTSワーカー
                                       ↑ 登録済みWAV由来の参照プロンプト
    ↓ 訳文と音声、または段階イベント + PCMチャンク
ブラウザー: 順序を守って再生、原文/訳文表示、Esc停止
```

### 最初の段階: 短文一括処理

- 日本語の一文を最後まで翻訳してから、英語を一括生成。訳文と完成WAVを返す。
- 既存再生処理を活用する。追加APIではメタデータ取得と音声取得を分離し、日本語を無理にHTTPヘッダーへ格納しない。
- 翻訳器とTTSの共通インターフェースを設け、モデル差をアプリ全体へ広げない。
- 翻訳のみ先行できるようにするが、同じGPU上の並行実行は計測してから有効化する。
- 原文で160文字でも英語では長くなるため、翻訳結果の上限とTTS固有のトークン・秒数上限を別々に検証する。Irodoriのsteps/speedをそのまま新モデルへ渡さない。

### 次の段階: 音声の逐次再生

公称ストリーミング能力と、実際に部分音声を取り出せる実装を区別する。調査時点のQwen標準Python実装は、generate後にdecodeして完成波形を返しており、`non_streaming_mode=False`を指定するだけでブラウザーへ逐次音声を返せるとはいえない。[3]

一方、vLLM-Omniの現行公式例にはQwen3-TTSのPCM/WebSocket対応が記載されている。Qwen本体READMEの「offlineのみ」という記述との時点差があるため、実験では採用するコミットと機能を固定して確認する。[4] Windowsネイティブで動くと仮定せず、WSL2/Linux側の別ワーカーも比較対象とする。

- サーバーから音声開始情報（sample_rate/channels/format）と、job_id/segment_id/sequence付きPCMを返す。
- ブラウザーはAudioWorkletと小さな再生バッファを使い、全体decode完了待ちをなくす。
- 途切れを防ぐバッファ量と開始遅延を同時に計測する。受信が速くても再生速度に追いつかなければ採用しない。
- 翻訳はまず文単位で確定してから渡す。日本語の文末否定などで意味が変わるため、未確定の英訳トークンを即発話しない。
- 複数文は確定した第一文から生成し、その再生中に第二文の翻訳・生成を進める。入力の途中で勝手に発話する仕様にはしない。

## 声プロファイルの移行

既存の元WAVは再利用候補だが、Irodoriのlatentは使い回さない。声の共通IDに、モデル別の参照情報をひも付ける。

保存項目案: `voice_id`, `reference_wav_hash`, `reference_language`, `reference_transcript`, `engine`, `model_revision`, `prompt_version`, `english_ready`。

- 自分の声: 既存WAVを保持。文字起こしを登録時・準備時に作り、本人が訂正できるようにする。文字起こしは発話ごとに行わない。
- designの声: まだWAVがなければIrodoriで一度だけ参照を作成し、その生成文を文字起こしとして記録する。声の準備は発話前に済ませる。
- presetの声: 元WAVの所在と内容を確認してから英語用参照を準備する。声名だけで再現できると扱わない。
- 異なるモデルでの同一声は完全一致を保証しない。本人録音、既存生成声、英語録音を評価セットで分ける。
- プロファイル削除時は英語用プロンプトも削除し、キャッシュを無効化する。録音・特徴量は現在と同様に配布から除外する。

## ジョブ・保存・運用で必要な変更

- `SpeechJob`に原文・訳文・source/target_language・声の版・翻訳モデル・TTSモデル・生成設定・キャンセル状態を保持する。
- API案: ジョブ作成、イベント購読、完成音声取得、取消。取消は冪等にし、ジョブIDで二重生成を抑止する。
- 発話順は受付順。先に翻訳が終わった文が追い越さない。翻訳先読みは有界キューで制限する。
- 停止は即座にブラウザーの音とバッファを止め、ワーカーは可能な生成ステップ境界で止める。停止できない処理でも結果を破棄し、次ジョブを塞ぐ時間を測る。
- モード変更は次回送信から適用。送信済みジョブの言語や声を後から変えない。
- 翻訳キャッシュと音声キャッシュを分離。翻訳側は原文・言語・用語集・翻訳モデル版、音声側は確定訳文・声WAV版・TTSモデル版・生成設定を含める。
- 履歴APIとUIに原文/訳文/言語を追加。履歴保存オフの意味を維持し、翻訳キャッシュも個人文を無制限に永続化しない。
- 英語ワーカーは専用環境。既存Irodoriの依存を上書きしない。ローカルHost/Origin制限と、プロセスを限定した停止を維持する。
- 英語モード準備時にTTSと参照をウォームアップする。毎回のモデル入れ替えは避ける。16GBに収まらなければ日本語モデルの待機時解放やCPU翻訳を比較し、切替待ちを表示する。

## 低遅延の判定方法

```text
送信から聞こえ始めるまで
  = 待ち行列 + 翻訳確定 + TTS初回音声
    + 転送/再生バッファ + 音声先頭無音 + 出力機器遅延
```

一括生成では「TTS初回音声」が事実上「全文生成完了」になる。翻訳の最初のトークン到着だけを短縮しても十分ではない。

| 条件 | 見込みの評価 | 必要な証拠 |
| --- | --- | --- |
| 登録済み定型句 | 翻訳・音声の事前生成で最も速くできる | 英語キャッシュ再生、設定変更後の無効化 |
| 初見の短文、準備完了済み | 低遅延化の主対象 | 翻訳込みp50/p95、英語の正確さ、声の似方 |
| 長文・複数文 | 一括処理では待ちが増える | 文分割または逐次音声の効果、継ぎ目、追従速度 |
| 起動直後・声の初回使用 | モデル/参照準備が支配的 | コールド値をウォーム値と別集計 |
| 100ms級の翻訳込み発話 | 今回の根拠では約束できない | 実機での全経路の計測が必要 |

日本語→英語では語順が変わるため、入力途中からの完全な同時発話より「Enterで確定→短時間で開始」を第一目標とする。

## 次に行う実証実験

1. 専用ワーカーで英語固定文のTTS単体を測る。Qwen Base 0.6B/1.7B、必要ならChatterboxを比較。まず元WAVをコピーせず参照し、既存環境を変更しない。
2. 既存設計声・本人の日本語WAV・本人の英語WAV（提供できる場合）で同じ英文を生成し、本人が似方を評価する。英文の明瞭さは英語を評価できる人の聴取と文字起こしで確認する。
3. OPUS-MTと翻訳品質候補を比較。短い会話、依頼、否定、金額、日時、人名、主語省略を含む固定セットを用いる。
4. 代表短文30件を各3回以上、長文・連投・取消も実行。コールドとウォーム、キャッシュ命中を別記する。最適化前後で同じセットを使う。
5. 一括方式で目標に届かなければ、実際にチャンクが早期到着するランタイムとAudioWorklet再生を試す。

測定項目: 翻訳完了、TTS先頭チャンク、全文生成完了、受信、再生スケジュール、先頭無音、RTF（生成時間/音声時間）、最大VRAM、音切れ、キャンセル後に次ジョブを開始できるまでの時間。p95は試行数も併記する。

採用条件案: 短文のウォーム再生開始目標を満たす、ストリーミングで生成が再生に追いつく、重大な否定・数字の誤訳がない、本人が声を許容できる、連投/Escで古い音声が出ない、既存日本語モードが動く。物理的な発話開始はループバックや外部録音で別測定し、ブラウザー計時から断定しない。
