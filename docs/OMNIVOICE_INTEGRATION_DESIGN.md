# OmniVoice導入・日英発話 統合設計

作成日: 2026-10-19。状態: 実装前の設計案。アプリ本体・モデル・環境設定は未変更。

本書を今回の実装方針とする。関連文書: [読み辞書詳細仕様](JAPANESE_READING_DICTIONARY_SPEC.md)、[比較評価・実装計画](OMNIVOICE_VALIDATION_PLAN.md)。既存の英語モード調査と候補比較は技術調査資料として残す。

## 1. 目的と採用判断

- 日本語入力を、選んだ声で日本語または英語として話す。
- OmniVoiceを日本語・英語の共通候補として導入し、現在のIrodoriと比較できるようにする。
- 日本語の読み間違いは、TTSへ渡す直前の読み辞書で訂正できるようにする。
- 日本語の標準エンジンは比較完了までIrodoriを維持。OmniVoiceが読み・声・速度で採用条件を満たせば、設定で標準を変更できるようにする。
- モデルの採用とアプリ構造を分離する。OmniVoiceが不採用でも辞書とジョブ管理は利用できる。

日英の声を同じ参照WAVへひも付けるが、同一の声質やアクセントを保証しない。Irodoriで作った参照WAVをOmniVoiceへ渡す経路は比較対象とし、本人録音とは分けて評価する。

### 対象範囲

今回設計: エンジン選択、声の準備、読み辞書、翻訳との分離、発話キュー、取消、キャッシュ、履歴、互換性、評価。

最初の実装に含めない: 入力途中の自動送信、マイクからの同時通訳、声の追加学習、音素/アクセント辞書、自動的な標準エンジン変更、公開配布や商用採用の確定。

## 3. 利用者の操作

発話画面には「日本語」「英語に翻訳」の切替、声選択、入力欄、発話、停止を置く。Enter/Shift+Enter/EscとIME変換中の送信抑止を維持する。

- 日本語: 原文入力→必要なら「読みを確認」→発話。確認操作は任意で、通常はEnterですぐ受付する。
- 英語に翻訳: 日本語原文入力→翻訳中→英文表示→英語発話。日本語読み辞書を翻訳前に適用しない。
- 読みが違う場合: 原文の単語と読みを辞書へ登録し、プレビュー後に再発話する。
- 声の準備中: 「この声を準備しています」と表示し、準備完了後に送信可能にする。
- エンジン: 通常は設定画面で選ぶ。比較時だけ「Irodori / OmniVoice」の選択を発話画面に表示する。

日本語標準と英語標準は別設定。英語はOmniVoiceを選べるが、Irodoriを英語へ指定した場合は受付時にエラーにする。失敗時に別の声・エンジンへ無断で切り替えない。

読みプレビューは見た目の確認であり、発音の保証ではない。辞書は漢字の読みを指定できるが、ピッチアクセントを直接指定するものではない。

## 4. 構成

```text
ブラウザー
  │ 原文・モード・声・クライアント要求ID
FastAPI 制御層
  ├─ 設定/辞書/声の版を受付時に固定
  ├─ 発話ジョブ管理・履歴・キャッシュ
  ├─ 日本語: 原文 → 読み辞書 → 発話文
  └─ 英語: 原文 → 翻訳ワーカー → 英文=発話文
       │
  TTS実行管理（GPU同時実行を制限）
       ├─ Irodoriアダプター → 専用ワーカー
       └─ OmniVoiceアダプター → 専用ワーカー
       │ 完成WAV + 計測情報
ブラウザー Web Audio 再生 → 任意の履歴保存
```

### 依存とプロセス

制御層はTorch/Irodoriをimportせず、声の音声検査などは適切な音声処理層へ委譲する。TTSごとのPython環境、モデル、HFキャッシュ、ログを分離する。現Irodori環境のライブラリーをOmniVoice導入で更新しない。

ワーカーは継続起動し、各ワーカーで1モデルを管理する。内部APIはloopbackのみ、起動時のランダムトークンで認証する。利用者のブラウザーは内部APIへ直接接続しない。ポートは設定可能とし、既存サービスと競合したら起動を中止して表示する。

内部契約は`GET /health`、`POST /load`、`POST /unload`、`POST /prepare-voice`、`POST /synthesize`、`POST /cancel`を基本とする。制御層からは利用者指定のファイルパスを受け渡さず、検証済み声IDから解決したパスだけ渡す。リクエストにjob_idとモデル/声の固定版を含め、ワーカー側の実モデル版と違えば失敗させる。初期タイムアウト案はロード180秒、声準備120秒、推論60秒。計測後に設定で調整し、無限待機しない。

例示配置: `runtime/omnivoice/`、`.runtime/workers/`、`data/voice-prompts/omnivoice/`。実パスは設定で解決し、配布に個別PCの絶対パスを埋め込まない。別サービスのモデル・プロセスを変更しない。

### エンジン共通インターフェース

| 操作 | 入出力・契約 |
| --- | --- |
| `capabilities()` | supported_languages、waveform/stream対応、設定の許容値、モデルrevision |
| `load()/unload()` | 常駐状態を変更。アクティブ推論中はunloadしない |
| `prepare_voice(profile_version)` | 元WAVと正確な文字起こしからエンジン専用参照を準備 |
| `synthesize(request)` | 確定発話文、言語、固定済み声参照、モデル別設定→音声と計測値 |
| `cancel(job_id)` | best-effort。非対応なら「実行中処理は完了待ち」と通知し結果を破棄 |
| `health()` | プロセス生存・モデル読込・参照準備・エラーを区別 |

OmniVoiceの通常APIは完成波形を返すため、第一版も完成WAV方式とする。将来のstream機能は能力が実証されたエンジンだけ有効化する。「内部長文分割」を早期音声配信と同一視しない。

## 5. 文章の分離

| フィールド | 日本語モード | 英語に翻訳 |
| --- | --- | --- |
| `original_text` | 入力した原文 | 日本語原文 |
| `translated_text` | null | 翻訳結果の英文 |
| `speech_text` | 日本語原文へ読み辞書を適用した文 | 確定英文 |
| `target_language` | ja | en |
| `reading_revision` | 固定した辞書版 | null（適用しない） |

原文は修正・上書きしない。翻訳用の固有名詞表記・用語集は将来別機能とし、日本語のかな読みに置き換えない。参照音声の文字起こしにも読み辞書を適用しない。

第一版は原文最大160 Unicodeコードポイント、読み適用後最大320、確定英文最大640を上限案とする。上限超過時に切り捨てない。モデル側トークン上限も受付後・推論前に確認し、超えたら明示エラー。ブラウザーの文字カウンターも`Array.from(text).length`で統一する。

第一版の音声は各ジョブ最大30秒、履歴WAVは現行と同じ31秒/10MiB上限を維持。OmniVoiceのdurationは上限設定ではないため、30秒に固定して発話を引き伸ばす使い方はしない。推定が範囲外なら生成前に拒否し、生成後も長さを検証する。将来の複数文分割は別仕様とする。

## 6. ジョブと停止

新UIは送信時にサーバーへジョブを登録する。現行の「ブラウザーで待ち、後からPOST」のままだと辞書や設定の固定時点が曖昧になるため、新経路ではサーバーを受付順の正とする。

状態: `queued → translating → waiting_engine → synthesizing → ready`。日本語ではtranslatingを省略。終端は`ready / failed / cancelled`。再生状態`playing/played`はブラウザー内で管理する。

- client_idごと最大8件、全体最大32件（稼働中＋待ち）を上限案とし、超過時429。過去ジョブの保持枠は別に上限を設ける。
- 受付時にエンジン・モデル版・声版・辞書版・翻訳設定を固定する。後から設定変更しても既存ジョブを変更しない。
- 出力順は同じクライアントの受付順。失敗・取消はスキップし、後続へ進む。
- 第一版は翻訳とTTSを含むGPUタスクを原則逐次実行。CPU翻訳の先読みは別途計測後に導入する。
- Escは音声を即停止し、ブラウザー世代を進め、そのクライアントの未完了ジョブを取消。古いready応答は再生しない。
- HTTP中断だけでGPU計算が止まったと扱わない。取消後の遅い結果は音声キャッシュ・履歴へ保存しない。
- 完了と取消はジョブ単位のロックで確定順を決める。保存済み定型句の共有キャッシュは、あるジョブの取消だけで削除しない。取消はそのジョブの公開結果と、以降の保存・再生を止める。
- ワーカーが止められない場合、タイムアウトまで現在処理を待つ。監督層がハングと判定した場合だけ所有するワーカーを再起動し、他アプリを停止しない。
- アプリ再起動時に未完了ジョブを自動再開しない。要求IDは起動セッション内の冪等性だけを保証する。

### GPUとモデル切替

第一版の既定は「直近利用モデルだけGPU常駐」。先頭ジョブが別エンジンなら、推論終了後に現在モデルをunloadし、必要モデルをloadする。FIFOを保持し、設定変更でキュー内ジョブを差し替えない。切替時間はUIへ表示し、ウォーム性能と分けて測る。

日英ともOmniVoiceならTTSの入替えを避けられる。翻訳との同時常駐はVRAM計測で有効化する。比較時の同時常駐も任意設定とし、OOM後に他モデルを無条件ロードし直すループを作らない。

## 7. 声プロファイル

共通IDは既存`design:* / preset:* / custom:*`を維持。元WAVを正として、その下にエンジン別の参照を持つ。

追加項目: `profile_revision`, `wav_sha256`, `reference_language`, `reference_transcript`, `clip_start_ms`, `clip_end_ms`, `engine_prompts`, `english_reference_optional`。

- OmniVoice参照は公式推奨の3〜10秒を初期候補とする。既存WAVを上書きせず、利用区間を別記録する。
- 参照音声の文字起こしは声の準備時に作成・確認する。通常発話ごとにASRしない。モデルと必要資産が揃えばオフラインで準備する。
- 既存design声はIrodoriが一度作ったWAVを使い、生成文が保存されていなければ既知文と決めつけない。内容を文字起こしして確認する。
- OmniVoice参照プロンプトはモデル版・Codec版・WAVハッシュ・区間・文字起こし・前処理版を鍵に保存する。
- 登録音声が1〜3秒未満でも既存Irodori利用は維持。OmniVoice準備では短さを表示して再録音または別区間を案内する。
- 声削除と推論の競合を防ぐ。利用中の声版は内部で保持し、新規利用を禁止、取消後に参照とキャッシュを削除する。表示名変更は声版を変えない。

参照3〜10秒、参照の保存再利用、クロス言語時のアクセントは[OmniVoice公式README](https://github.com/k2-fsa/OmniVoice)の現行説明による。実際の声の品質は未検証。

## 8. 保存とキャッシュ

SQLiteの新テーブル案: `reading_dictionary`（revision＋entries JSON）、`voice_profiles`（共通メタ）、`engine_voice_prompts`（参照の版とローカル成果物）。ジョブと未保存音声はメモリー管理とし、履歴保存オン時だけ履歴へ記録する。

音声キャッシュキー: schema版、engine、コード/モデル/Codec版、言語、確定speech_text、辞書版（jaのみ）、声版、エンジン設定、速度、seed方針、透かし/後処理設定。翻訳キャッシュは原文・翻訳モデル版・用語集版・翻訳設定で分離する。

キャッシュ初期方針: 通常の自由入力はディスク保存しない。定型句の事前生成だけ明示的に保存。辞書更新後は新キーを使い、古い音声を新設定の音声として返さない。履歴再生は保存済み音声を再生し、辞書変更で再生成しない。

履歴には原文・訳文・発話文・エンジン/モデル版・声版・辞書版・実際の生成日時・計測を記録。保存は完成して再生を開始したジョブについて一度だけ行い、取消・失敗の音声は保存しない。保存オフはタブ内保持のみ、再読込で消える既存方針を維持する。

一時結果の上限案: 完成音声128MiB、終端ジョブ100件、最終アクセス15分。保持できない場合は古い終端結果から破棄し410を返す。ready音声を取得したブラウザーはBlobとして保持し、サーバー破棄後もそのタブで再生できる。参照WAV・参照特徴は声の登録データであり、履歴保存設定とは別に管理する。

## 9. API契約案

既存`POST /api/speech`は日本語・完成WAVの互換経路として維持する。新しいUIは以下の`/api/v2`を使う。両経路のTTS実行は同じ管理層を通し、別ロックでGPUを競合させない。

| API | 契約 |
| --- | --- |
| `GET /api/v2/engines` | 言語、状態、モデル版、設定許容値 |
| `POST /api/v2/speech-jobs` | 原文・mode・voice_id・engine任意・engine_settings・client_id・request_idを検証し202 |
| `GET /api/v2/speech-jobs/{id}` | 状態、確定原文/訳文/発話文、固定版、計測、エラー |
| `GET /api/v2/speech-jobs/{id}/audio` | readyならWAV。未完了409、取消410、音声破棄済み410 |
| `DELETE /api/v2/speech-jobs/{id}` | 冪等な取消。readyも取得停止可能、既再生音はブラウザーで停止 |
| `POST /api/v2/clients/{id}/cancel` | そのクライアントの一括取消 |
| `POST /api/v2/voices/{id}/prepare` | 非同期の声準備、状態照会。推論とGPU実行枠を共有 |
| `GET /api/v2/voices/{id}/preparation?engine=omnivoice` | 固定声版ごとの未準備/準備中/完了/失敗とモデル版 |
| `GET/PUT /api/v2/reading-dictionary` | 版付き辞書取得・原子的更新 |
| `POST /api/v2/reading-preview` | GPUを使わず辞書適用結果を返す |

第一版のジョブ状態通知は250〜500ms程度のポーリング（ready受信で即音声取得）。この間隔も体感遅延に含める。必要ならlong-pollへ変更し、音声チャンク配信とは分けて扱う。

```json
{
  "client_id": "tab-71",
  "request_id": "req-92",
  "mode": "ja",
  "engine": "omnivoice",
  "voice_id": "custom:my_voice_abcd1234",
  "text": "日本橋で待っています。",
  "speed": 1.0,
  "engine_settings": {"num_step": 32},
  "use_phrase_cache": false
}
```

202応答例（ID等は例示）:

```json
{
  "id": "job-18",
  "state": "queued",
  "snapshot": {
    "engine": "omnivoice",
    "target_language": "ja",
    "voice_revision": 2,
    "reading_revision": 7,
    "original_text": "日本橋で待っています。",
    "translated_text": null,
    "speech_text": "にほんばしで待っています。"
  }
}
```

同一client_id/request_id・同一payloadは同じジョブを返す。異なるpayloadの再利用は409。辞書更新後の再送でも同じ要求IDなら元スナップショットを使う。別発話は新しい要求IDを作る。

受付時の入力不正422、辞書版競合409、未準備エンジン/声503、上限429。受付後の翻訳/合成エラーはジョブの`failed`へ記録し、状態GET自体は200。エラーには`code`, `message`, `stage`, `retryable`を持たせる。内部パスや原文を通常ログへ出さない。

ブラウザーごとにsessionStorageへclient_idを生成する。これは順序・取消の識別子であり、認証には使わない。全公開APIは現行のHost/Origin制限を継承し、状態変更GETを設けない。

## 10. エンジン別設定と起動

Irodoriの4/6/8 stepsとOmniVoiceのnum_stepを同じ設定欄・保存値にしない。OmniVoiceは標準32、比較用16を初期許容値とし、speedは現行0.7〜1.5を維持。durationは通常UIから指定しない。値は採用するモデル版で検証する。

OmniVoiceのnum_step/speed/後処理は[公式パラメータ資料](https://github.com/k2-fsa/OmniVoice/blob/master/docs/generation-parameters.md)に基づく。公式の既定を変更したらキャッシュキーと評価記録に残す。

設定はschema_versionを導入し、旧フラット構造をバックアップして移行。旧Irodori用パス・ポート・精度は保持し、各エンジン設定へ写す。初期移行時にモデルを自動ダウンロードしない。

起動時は選択したTTSと現在の声を準備し、未導入の別エンジンをロードしない。終了は所有PID・コマンドライン・起動識別子を確認して子ワーカーを終了する。健康確認はHTTP状態に加えて準備完了を確認する。

## 11. 代替案と採否

| 案 | 判断 |
| --- | --- |
| Irodoriを即座に削除してOmniVoiceだけにする | 比較・復帰経路がなくなるため保留 |
| 全TTSを同じPython環境へ入れる | 依存衝突を避けるため不採用 |
| 翻訳前に読み辞書で原文をかな化 | 意味・固有名詞を損なうため不採用 |
| 最初から全エンジンを同時常駐 | メモリ実測後の任意設定 |
| 短文一括生成から開始 | 採用。現UIとの接続と比較を先に成立させる |
| ストリーミングの独自改造 | 一括方式の測定後に必要性を判断 |

## 12. 未確定事項と実装への条件
